# 物品去留决策流程（Evaluation Workflow）

## 1. 采集：只问事实，不问判断

**用户来找你，正是因为他判断不了去留。** 所以不能要求他对"使用频率""情感强度""有没有必要"做量化自评，也不能让他预测未来——那等于把最难的部分推回给他。

分工：

- **用户讲事实**：上一次什么时候用的、现在还能不能用、从哪来的、放在哪儿。看一眼、想一下就能答。
- **系统做判断**：把事实翻译成六维分数，算出结论。

三条提问铁律：

1. 问**已经发生的事**，不问预测（不问"你会不会用"，问"上次用是什么时候"）。
2. 问**可观察的属性**，不问强度（不问"你有多在意它"，问"它是谁给的"）。
3. 选项用**用户会说的话**，不用量表术语；分数在内部映射，不暴露给用户。

## 1.1 六个口语问题与答案→分数映射

**Q1 上一次真正用到它，是什么时候？**（使用频率）

| 用户可能这样说 | 分 |
|---|---|
| 最近一两周还在用 | 5 |
| 最近几个月用过 | 4 |
| 大概一年前 | 3 |
| 去年或更早，一年里偶尔用 | 2 |
| 想不起来上次是什么时候 | 1 |
| 买来就没怎么用过 / 从没用过 | 0 |

**Q2 接下来一年，有没有具体哪件事会用到它？**（未来需求）

| 用户可能这样说 | 分 |
|---|---|
| 已经定好了，肯定会用（报了名的活动、约好的事） | 5 |
| 有固定的时候（换季、过年、每年一次） | 4 |
| 能想到具体场景，但不确定会不会发生 | 3 |
| 说不准，就是觉得万一用得上 | 2 |
| 想不出什么事 | 1 |
| 情况变了，肯定用不上了 | 0 |

**Q3 现在还能用吗？**（功能状态）

| 用户可能这样说 | 分 |
|---|---|
| 能，跟新的差不多 | 5 |
| 能用，有正常使用痕迹 | 4 |
| 能用，但得修一下或换配件（换电池、补零件） | 3 |
| 得大修才行 | 2 |
| 勉强能用，快不行了 | 1 |
| 用不了了：坏了 / 过期 / 变质 | 0 |

**Q4 如果现在需要，还能再弄到一个吗？**（替代难度）

| 用户可能这样说 | 分 |
|---|---|
| 弄不到了：绝版、独一无二、别人手工做的 | 5 |
| 能，但很贵，或者得费劲找 | 4 |
| 得专门跑一趟或下单等几天，中等花费 | 3 |
| 网上随手就能买，也不贵 | 2 |
| 随处都有，很便宜 | 1 |
| 家里还有好几个 | 0 |

问的是"重新获得"，不是"当初花了多少"。用户若说"当年买成三千"，仍按现在能否买到估分。

**Q5 它是从哪来的？**（情感价值）

| 用户可能这样说 | 分 |
|---|---|
| 重要的人给的或留下的 | 5 |
| 某次特别的经历带回来的 | 4 |
| 自己买的，用了很久有点感情 | 3 |
| 有点喜欢，没什么特别来历 | 2 |
| 随手买的 / 别人给的，无感 | 1 |
| 看到就烦，或者连着不愉快的事 | 0 |

不问"你有多在意它"，问来源——来源答得出，强度由系统判断。后悔"花了不少钱"不算情感，按 1 分。

**Q6 它现在放在哪儿，占多大地方？**（空间友好度）

| 用户可能这样说 | 分 |
|---|---|
| 随手就能拿到，几乎不占地方 | 5 |
| 收在一个小格子里 | 4 |
| 占一格层板或一个抽屉 | 3 |
| 占半个柜子 | 2 |
| 算大件，占一整柜 | 1 |
| 专门腾了地方放它：一个角落 / 一间房 | 0 |

最后补一句硬规则确认：`有没有过期 / 修不了 / 是证件合同 / 有安全隐患？`（可跳过）。

## 1.2 追问校验（分数模棱两可时用）

两句具体场景题，不需要判断力：

- **「如果它现在不见了，你大概什么时候会发现？」**
  两三天内 → 使用频率 ≥ 4；一两个月后 → 3；大概永远不会 → ≤ 1
- **「如果现在要花两百块重新买一个，你会买吗？」**
  会 → 未来需求 ≥ 4 且替代难度 ≥ 3；不会 → 未来需求 ≤ 2

## 1.3 展示与确认

把推断出的分数连同**依据**一起摊给用户，请他纠正事实，而不是改分数：

> 我按你说的估了一下：
>
> - 上次用：去年夏天（使用频率 1）
> - 还能用：铝合金杆体完好（功能状态 4）
> - 重新买：网上两三百能买到（替代难度 2）
> - 来历：自己买的，没什么特别（情感价值 1）
> - 放哪儿：阳台柜子占一格（空间友好度 3）
>
> 哪条说错了直接告诉我（比如"其实去年冬天还用过一次"），没有就回"确认"。

带依据是关键：只给孤零零的数字，用户无从反驳。用户纠正的是**事实**，分数随之自动改。

## 1.4 快速模式（一次清理很多件时）

只问三题，用户口头就能答：

1. 上次用它是什么时候？（按 Q1 表）
2. 现在还能用吗？（按 Q3 表）
3. 它是从哪来的？（按 Q5 表）

其余维度按 1.5 默认值补齐。快速模式只用于排序和初判，结论标为"初判"，拿不准的件再走主流程。

## 1.5 答不出时的默认值（就低不就高）

| 维度 | 默认值 | 理由 |
|------|--------|------|
| 使用频率 | 2 | "记不清用过"通常等于很少用 |
| 未来需求 | min(使用频率, 2) | 说不清不等于会用 |
| 功能状态 | 3 | 中性；明确损坏才取 0 |
| 替代难度 | 3 | 中性 |
| 情感价值 | 1 | 真正有来历的物品用户一定会说出来 |
| 空间友好度 | 3 | 中性 |

任何默认值都必须在报告中标注"该项为默认取值，确认后可重算"。

## 1.6 界面选项（`--interactive` 与网页表单）

命令行交互与网页表单的选项是**口语答案**，不是分数档位——用户看到的是"最近一两周还在用"这类话，数字由界面内部处理。仅在用户愿意自己逐项选择时使用；对话场景一律走 1.1 的口语提问。

## 2. 输入 JSON Schema

`scripts/assess_item.py` 接受单个对象或 `items` 数组：

```json
{
  "items": [
    {
      "name": "旧登山杖",
      "scores": {
        "usage": 1,
        "future": 2,
        "condition": 4,
        "replace": 3,
        "sentiment": 2,
        "space": 3
      },
      "evidence": {
        "usage": "去年搬家后没再拿出来",
        "future": "没有计划爬山，只是想着万一"
      },
      "flags": [],
      "notes": "铝合金材质，可折叠"
    }
  ]
}
```

字段说明：

- `name`：物品名称，必填。
- `category`：品类 key（见 `category-priors.md`），可选；给了之后，未提供分数的维度按该品类基线推断，并自动带上品类自带的硬规则标记。
- `scores`：六维度得分，缺省时先按品类基线推断，无品类则按 0 处理并告警；超出 0–5 直接报错。
- `evidence`：逐维度证据（用户原话），可选，强烈建议填；缺失会在报告中标记。
- `economy`：`tight` / `normal` / `comfortable`，可选，默认 `normal`；影响替代难度的价格换算与处置路径建议。
- `owner`：归属，可选，默认 `self`。填伴侣 / 孩子 / 父母 / 室友等时，结论标注"需协商"，且不参与同类冗余自动调整。
- `flags`：`safety` / `expired` / `irreparable` / `document`，可选，触发硬规则。
- `swings`：摇摆次数，可选。1 = 结论拉到封存观察并写明复评日期；≥2 = 锁定，只输出执行动作。
- `depends_on`：主件名称（同批里的 `name`），可选。主件结论为处理类时，本件的使用频率与未来需求清零，结论不低于建议流转（情感 ≥4 改为封存观察）。
- `host_gone`：`true` 表示主件已不在（已转卖 / 已坏 / 已送人），用于主件不在本批时。与 `depends_on` 二选一即可。
- `wtp`：WTP 检验的答案——今天愿意花多少钱再买一个（数字）。填了之后替代难度按该金额与经济档位换算，报告中来源标为"WTP 检验"。
- `notes`：补充说明，可选，原样带入报告。

单个物品可直接写对象（不带 `items` 包裹）。

## 3. 命令

```bash
# 交互问答（逐项给出口语选项，用户挑一个）
python scripts/assess_item.py --interactive

# 默认方案评估
python scripts/assess_item.py --input items.json

# 换权重方案
python scripts/assess_item.py --input items.json --preset minimalist

# 微调权重（未指定的维度沿用方案值，自动归一化）
# 推荐 key=value 写法，避免不同 shell 的引号转义问题；也支持 JSON 对象形式
python scripts/assess_item.py --input items.json --preset space --weights sentiment=0.05,usage=0.35
python scripts/assess_item.py --input items.json --preset space --weights '{"sentiment":0.05}'

# 输出 Markdown 报告 + HTML 可视化 + 结构化结果
python scripts/assess_item.py --input items.json --out report.md --html report.html --json result.json

# 指定品类（未填的维度按品类基线推断）
python scripts/assess_item.py --input items.json --category phone_box

# 分组容量：按品类分别设上限；也支持纯数字作全局上限
python scripts/assess_item.py --input items.json --capacity "book:10,clothing:20,cable:3"
python scripts/assess_item.py --input items.json --capacity 3

# 关闭同类冗余（同用途只留一件）
python scripts/assess_item.py --input items.json --no-redundancy

# 封存档案：写入需复评的物品 / 查看到期项
python scripts/assess_item.py --input items.json --log seal.json
python scripts/assess_item.py --review seal.json

# 规则数据同步到网页表单（改动规则后运行），--check 只校验
python scripts/build_form.py
python scripts/build_form.py --check

# 标定回归（改动规则后运行），不符返回退出码 1
python scripts/calibrate.py
python scripts/calibrate.py --preset minimalist --quiet

# 指定经济档位 / 把价格换算成替代难度分
python scripts/assess_item.py --input items.json --economy tight
python scripts/assess_item.py --price 200 --economy comfortable

# 列出内置权重方案 / 品类基线 / 经济档位
python scripts/assess_item.py --list-presets
python scripts/assess_item.py --list-categories
python scripts/assess_item.py --list-economy
```

交互界面（无需命令行）：直接用浏览器打开 `assets/assessment-form.html`。

## 4. 汇总算法

1. 权重归一化：`w' = w / Σw`（自定义权重总和不为 1 时自动归一化并提示）。
2. 维度归一化：`s = score / 5`。
3. 加权总分（百分制）：`total = 100 × Σ(w' × s)`。
4. 按分档表映射结论；批量时按总分升序生成处理优先级。

## 5. 权重调整指引

- 先用 `balanced` 算出基线，再按用户反应切换方案重算——**改权重，不改分数**。
- 用户说"我就是舍不得" → `sentimental`。
- 用户说"家里太挤了" / 准备搬家 → `space`。
- 用户说"想彻底精简" → `minimalist`。
- 单维度权重建议不超过 0.4，避免一个维度决定全部结果。
- 权重调整后结论若与用户直觉冲突，把维度贡献表展示给用户，让其自行确认哪个维度估错了。

## 6. 复评机制

- 「暂存观察」「保留（观察）」的物品应记录封存日期与复评日期。
- 复评时若使用频率仍为 0–1 且未来需求 ≤ 2，直接降为「建议流转」。
- 批量清理时，优先处理"总分最低 + 空间友好度最低"的物品，空间收益最大。

## 7. 摇摆处理话术

结论说"丢"之后用户反悔，是必然发生的，不是意外。以下话术按序使用，不要临场发挥。

### 7.1 打分前：立规矩

> 分数出来后我们照结论执行。之后想改，得拿出**新的事实**——光说"还是舍不得"不算，舍不得已经在情感价值那一栏里了。

### 7.2 第一次反悔（"算了还是留着吧"）

先分辨有没有新事实：

- **有新事实**（"其实保修还有半年"）→ 改对应维度，重算，说明改了哪一项、结论变成什么。
- **只有情绪** → 不改分数，走到封存：

> 这不是新信息，分数不变。但你既然犹豫，我们不硬丢——改成**封存观察**：装箱、写上今天的日期和复评日期（3 个月后）。到期你如果一次都没打开，就直接处理，不再重新权衡。
>
> 这不是折中，是给犹豫一个出口：既不丢，也不让它继续占着你的地方。

### 7.3 第二次及以后：锁定

> 结论已经锁定在封存了。接下来只有一件事：装进箱子、贴好日期。剩下的交给 3 个月后的你——那时候你打开箱子看一眼就知道答案，比现在想一百遍都准。

之后用户再摇摆，**不再重算、不再解释**，只重复执行动作。回复要短、要和前一次一致。

### 7.4 对方要求你给出"留下"的理由

直接说明立场，不要配合：

> 我可以帮你把依据再摆一遍：它 46 分，主要是使用频率 0、未来需求 1。我也可以把这改成封存，给你三个月缓冲。但我不会为了让你现在好受一点，就说"留着吧"——那等于让你下次再纠结一遍同样的事。

### 7.4.1 后悔管理（封存为什么有效）

用户怕的不是失去，是**怕以后后悔**——这是封存观察的理论位置，三条设计都由此推出：

| 概念 | 出处 | 推出的设计 |
|---|---|---|
| 预期性后悔 / 后悔最小化 | Zeelenberg et al., 2000 | 结论要给"后悔的出口"，而不是更强的论证 |
| 后悔的作为效应：做了比没做更后悔 | Kahneman & Tversky, 1982 | 只能单向移动到封存（不作为侧），不往丢弃加码 |
| 不作为惯性（错过一次后更不愿行动） | Tykocinski & Pittman | 出口只给一次，第二次起锁定 |
| 选择延期（没有期限就等于不动） | Tversky & Shafir, 1992 | 期限写死；到期未取用是**新事实**，不是重新权衡 |

保险说法（直接可用）：

> 封存是给"怕以后后悔"买的一份保险：保费是这三个月的空间，赔付条件是到期你一次都没打开过。它只卖一次，不续保——续保就等于永远不做决定。

脚本侧：物品加 `"swings": 1` → 结论拉到封存观察并写明复评日期；`"swings": 2` 及以上 → 锁定，只输出执行动作。`--log` 记录封存/复评日期与摇摆次数，`--review` 到期只提示"取用过就重评，没取用就按原结论处理"。

### 7.5 常见理由的处理

| 用户说 | 机制 | 回应 |
|---|---|---|
| "以后可能会有用" | 沉没成本 | 「具体是哪件事？大概什么时候？」答不出 → 未来需求 ≤ 2，维持结论 |
| "我妈 / 我老婆说留着有用" | — | 「那是她的需求还是你的？」他人的期待不加未来需求；若因此有压力，情感价值记 2–3 分并说明 |
| "当年买的时候挺贵的" | 沉没成本 | 那笔钱已经花完，留和不留都收不回来；替代难度问的是"现在能不能再弄到" |
| "这个挺值钱的 / 不好买了" | 禀赋效应 | 「如果它现在不在你家，**今天**你愿意掏钱再买一个吗？愿意出多少？」——用买价替换卖价；答不出数字按不会买，`--price <金额> --economy <档位>` 换算替代难度 |
| "它还能用呢" | — | 「你还在用吗？」——能用只说明可以送人，不说明该留（主轴是你，不是它） |
| "总有一天会用上" | — | 「哪一天？做什么用？」说不出日期就等于永远不会 |
| "扔了可惜" | 损失厌恶 | 可惜已经算在情感价值里了（就是那个 2 分）；不重复计算 |
| "还是舍不得 / 心里不踏实" | 损失厌恶 | 这不是你脆弱，是大脑默认机制：失去的痛感约为得到的两倍。不改结论，改出口——封存三个月 |
| "万一以后后悔呢" | 损失厌恶 | 后悔的风险用封存对冲，不用保留对冲——封存给了你三个月反悔期 |

命中这三件套时，脚本会在报告正文打出「心理偏差提示」，可以直接念给用户；完整话术见 SKILL.md「行为经济学三件套」。

## 8. 经济档位校准

同一个物品对不同经济状况的人应有不同结论。核心是**替代难度的价格阈值**随档位缩放：

| 档位 | key | ≥200 元 | ≥1000 元 | ≥5000 元 | 低于最低锚点 |
|------|-----|---------|----------|----------|--------------|
| 预算敏感 | `tight` | 4 分 | 4 分 | 4 分 | 50–200 元记 3 分，<50 元记 2 分 |
| 常规 | `normal` | 3 分 | 4 分 | 4 分 | <200 元记 2 分 |
| 预算宽裕 | `comfortable` | 2 分 | 3 分 | 4 分 | <1000 元记 2 分 |

换算不必手算，直接用命令：

```bash
python scripts/assess_item.py --price 200 --economy tight
python scripts/assess_item.py --list-economy
```

定性判断优先于价格：明确"买不到了 / 独一无二"记 5 分，"家里还有好几个"记 0 分，都不受档位影响。

推断不出档位时用 `normal`，并在报告中标注"经济档位按常规判断，可调整"。

## 9. 断舍离与容量

### 9.1 三条规则的来源

更高一层的"为什么"见 SKILL.md「立意：占有，还是存在」：断舍离解决"怎么取舍"，弗洛姆的占有型 / 存在型回答"为什么必须取舍"——**把自我定义寄托在物品上，拥有的越多怕失去的就越多**。哲学只在用户问"为什么非要扔"时说一句，不作为每件物品的开场白。

| 断舍离主张 | 在本系统中的落地 |
|---|---|
| 主轴是"现在的我"，不是物品 | 使用频率 ≤1 且未来需求 ≤2 → 结论不得高于暂存观察，再新再贵也不算保留理由 |
| "总有一天" = 永远不会 | 使用频率 ≤1 且未来需求 = 2（万一用得上）→ 未来需求按 1 分计，并在报告中注明 |
| 不需要 · 不适合 · 不愉快 | 情感价值 = 0（看到就烦）→ 结论不低于建议流转 |
| 舍不是扔 | 功能状态 ≥4 却判丢弃 → 先问亲友或免费赠送，无人要再回收 |
| 不为过去买单（沉没成本谬误） | 替代难度只问"现在能否再弄到"，当初花销不计分 |

### 9.2 7·5·1 容量法则（帕金森定律的物品版）

**帕金森定律**（1955 年《经济学人》）：工作会膨胀到填满所有可用时间；物品版是同一结构——**东西会膨胀到填满所有可用空间**。旁证：UCLA《Life at Home in the Twenty-First Century》观察的 32 个中产家庭里，**75% 车库停不进车**；2023 年 Self-Storage Almanac 显示超过 **11%** 的美国家庭在租储物间给家里的膨胀"外包"。

所以顺序不能反：**先定容器，再选物品**；也别用"买个更大的柜子"解决取舍——那只是给膨胀扩容，顺便触发狄德罗效应（新柜子 → 新收纳盒 → 新标签）。清理完留下的空位是**膨胀余量**，不是浪费。

先定容器，再选物品，逐件纠结就消失了：

- 看不见的收纳空间（柜内、抽屉内）放 **7 成**
- 看得见的空间（台面、碗柜、开放式层板）放 **5 成**
- 展示性空间（装饰、摆件）放 **1 成**

批量评估时用 `--capacity N` 给出该区域或品类的总量上限，脚本按总分排序，超出部分直接标记"超出容量 → 按处理路径执行"：

```bash
python scripts/assess_item.py --input items.json --capacity 2
```

容量是**总量约束**，优先于单件结论：即便某件物品结论是"暂存观察"，只要它排在容量之外，也应按处理路径执行。

### 9.3 话术

- 对"还能用"：「它还能用，但**你在用吗**？断舍离里主轴是你，不是它。它能用只是意味着可以送人，不意味着该留在你这儿。」
- 对"总有一天会用"：「'总有一天'在断舍离里等于 never。要留，得说得出是哪天、做什么用。」
- 对"扔了可惜"：「可惜是对东西的执念。它完好的话，送给需要的人，比躺在柜子里有价值。」

## 10. 复核清单

输出结论前检查：

1. 六个维度都有分数，且方向未搞反（尤其空间友好度）？
2. 采集时是否只问了事实，没有让用户做去留判断或量化自评？
3. 是否已从用户原话和品类基线中抽尽信息，只对真正的缺口发问？
3. 总分由脚本算出，非手算？
4. 硬规则是否已判定（安全风险、过期、不可修复、不可替代凭证）？
5. 情感价值 5 分的物品是否输出了"丢弃"？（不应出现）
6. 结论是否带具体处置路径和一个本周内可完成的动作？
7. 批量清理时是否设定了容量上限（7·5·1），超出部分是否已标记？
8. 主轴是否始终是"现在的我"——有没有出现"还能用所以留着"这类以物品为轴的理由？
9. 物品是否属于他人？属于他人时是否已标注"需协商"而非直接给出处理建议？
10. 被判处理的物品，其**附属件**是否已一并入册（`depends_on` / `host_gone`）？避免"主件走了、配件留着"。
11. 改动过规则或阈值后，是否已重跑 `build_form.py` 与 `calibrate.py`？
