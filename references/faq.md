# 常见问题与反模式（FAQ）

> 这份文档集中回答"用的时候卡住了怎么办"。判断单件物品不需要读它；
> 用户追问、或者你发现自己在重复解释同一件事时，来这里找现成答案。

## 一、用户侧 FAQ

### 1. 我到底该不该扔？
不要问用户这个问题——他来找你，就是因为他判断不了。问事实：上次什么时候用、还能不能用、从哪来、放哪儿。判断由系统做。

### 2. 结论说"处理"，但我就是舍不得。
已经计入情感价值了，不重复计算。第 1 次反悔给封存观察（写明封存日期与复评日期）；第 2 次起锁定，只重复执行动作，不重新权衡。封存是给"怕以后后悔"买的一次性保险，不续保。

### 3. 这个挺值钱的 / 不好买了。
这是禀赋效应。用反问检验：**如果它现在不在你家，今天你愿意掏钱再买一个吗？愿意出多少？**
答案是数字才作数；说不出数字、答"看情况""以后再说"，按不会买处理（替代难度 ≤ 2，通常记 1）。

### 4. 当年花三千买的。
沉没成本。那笔钱已经花完了，留和不留都收不回来。只看从今天起的得失；当初花销不计入任何维度。

### 5. "万一以后有用"呢？
要具体场景才成立：具体是哪件事？大概什么时候？答不出 → 未来需求 ≤ 2；只说"总有一天"→ 按 1 分计，总有一天永远不会来。

### 6. 我妈说留着有用。
那是他的需求，不是用户的。未来需求不加分，最多计入情感价值 2–3 分（来自家人的压力）。

### 7. 结论出来后我能改吗？
只认**新事实**："其实保修期还有半年""我妹下学期正好要这本书""去年我妈还问过它"。改分数必须说明改了哪一项。情绪、假设、他人意见、犹豫都不构成改判理由。

### 8. 封存到期了怎么办？
到期未取用就是新事实，按原结论处理，不重新权衡。复评不是重新权衡，是核对事实：打开箱子看一眼，取用过就重新评分，没取用过直接执行。

### 9. 批量清理从哪件开始？
先定容器（7·5·1），再选物品；组内按总分升序处理（分数越低越优先），体积大的优先，收益最明显。批量 ≥5 件却没设 `--capacity` 时脚本会提醒。

### 10. 别人的东西怎么算？
结论照算，但标注"处置前需与对方协商，本结论仅供参考，不直接执行"——没有替别人做决定的权力。归属他人物品不参与同类冗余自动调整。

### 11. 主件没了，配件呢？
价值随主件一起清零。采集时必问一句："它是为哪件东西服务的？那件还在吗？"主件已不在 → 使用频率与未来需求按 0 计，结论不低于建议流转；情感 ≥4 改封存观察。

### 12. 什么时候不该用这个技能？
涉及法律、医疗、财务等专业判断时不适用；证件、处方药、危险废弃物按当地法规与专业渠道处理。这是决策辅助，不是专业意见。

## 二、命令行 FAQ

### 13. 报错"分数写在了顶层"。
分数必须嵌在 `scores` 里，写在顶层会被判定为未知字段。正确写法：

```json
{"name": "旧登山杖", "scores": {"usage": 1, "future": 2}}
```

### 14. 报错"不是合法 JSON"。
错误信息带第几行第几列。最常见原因：中文引号「」“”、字段末尾多了逗号、把注释写进了 JSON。用 `--interactive` 交互录入可以完全绕开手写 JSON。

### 15. 报错"不是 UTF-8 编码"。
文件是 GBK。用记事本另存为 UTF-8，或直接粘贴内容走 `--interactive`。

### 16. 提示"维度 X 未取得信息，按默认 0 处理，结论不可靠"。
说明这件物品既没给分数、也没匹配到品类。先补信息再重算，不要让这种结论出现在最终输出里。

### 17. 提示"权重总和为 x，已归一化到 1"。
`--weights` 不必凑够 1，脚本会自己归一化；想精确控制就用加起来等于 1 的数值。

### 18. `--out` 指向的目录不存在。
会自动创建（包括多级目录）；写不出去时会给出"写入失败 + 原因"，不会静默丢报告。

### 19. 想列出所有可选项。
`--list-presets` / `--list-categories` / `--list-economy`；完整参数见 `python scripts/assess_item.py --help`。

### 20. 封存档案读不了。
档案必须是本脚本生成的 JSON 数组。损坏时报错会带行列号——先修档案再 `--review`，不要手删文件。

## 三、反模式（不要这样做）

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 要求用户给"重要性 1–10 分" | 把最难判断题推回给判断不了的人 | 只问可观察的事实，分数由你翻译 |
| 为了缓解焦虑调分数 / 调权重凑"保留" | 系统退化成情绪镜子 | 犹豫的出口是封存观察，不是改结论 |
| 结论出来后顺着用户重新权衡 | 每次妥协都抬高下一次行动门槛 | 只认新事实；第 2 次起锁定 |
| 手算总分 | 权重归一化与硬规则容易算错 | 一律交给脚本，禁止手算 |
| 把"还能用 / 挺值钱"当保留理由 | 功能状态与替代难度说的是拥有，不是生活 | 闲置折半：这两维对长期闲置物减半计入 |
| 没有期限的"再缓一缓" | 没有期限的延期等于永远不动 | 封存必须写死复评日期 |
| 对每件物品都讲一遍哲学 | 立意是给执行者的行为指南，不是开场白 | 用户没问"为什么非要扔"就只给结论和动作 |
| 批量清理不设容量 | 清掉一件，剩下的会自动铺开补位 | 先定容器再选物品，并留空位当膨胀余量 |
